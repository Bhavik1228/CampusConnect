# Campus Connect

Campus Connect is the Vite + React application for the school information and learning management system. The existing `index.html` in the repository root remains the separate landing-page demo; the application lives in `app/`. The app's public `/` route is its product landing page, `/login` is for account access, and school workspaces are available after sign-in.

## V1 implemented in this workspace

- Supabase email/password authentication, persisted sessions, sign-out, email-confirmation redirects, and password-reset email requests
- School workspace creation for a newly signed-in account
- School membership and active-school selection
- Tenant-scoped PostgreSQL schema and row-level security policies
- Live school dashboard counts and attendance summary
- Student, teacher, class, and subject directory views, search, and administrator-only create flows
- Foundational academic, timetable, attendance, assignment, announcement, event, messaging, notification, audit, and private file-storage schema
- Responsive application shell, mobile navigation, loading/error/empty states
- School administrator settings for school identity and branding, grading and academic-year defaults, attendance policies, family/student portals, notification preferences, 45+ module/feature switches, and security/privacy policies
- School-scoped Test Maker for teacher-created and authorized-resource assessments, question libraries, configuration, and print-to-PDF previews
- Course and lesson management with subject/class/teacher assignments, ordered units, objectives and descriptions, publishing, and per-student completion tracking
- Learning-material library for PDF, Office, text, and video uploads, topic/subject/class organization, private previews/downloads, and class/school visibility
- School-admin-managed connections to multiple school-owned private R2 buckets, encrypted server-side credentials, optional Campus Connect-managed R2, and per-resource bucket selection
- System-owner dashboard for platform school/user/student/teacher totals, role statistics, school status management, platform activity, system alerts, and managed-storage request review
- Assignments and homework with class publishing, deadlines, instructions, attached learning resources, student text/file submissions, late-status tracking, and teacher marks/feedback
- Assessment result entry with validated marks, calculated percentages, and searchable student attempt histories
- Grades & results management with configurable school grading bands, teacher comments, approval and publication workflows, authorized audited corrections, student/parent result viewing, and individual or all-student PDF reports
- Five original report layouts plus school-customizable report templates with configurable titles, colors, subtitles, and footers
- School-admin-managed public websites with optional publishing, homepage content, admissions information, public fee tables, and optional student-number lookup for published results
- Staff directory with department and employment records, linked teacher qualifications, teaching subject/class allocations, and private school-admin-only staff document storage
- Teacher workspaces with daily/weekly timetables, assigned teaching, pending work, and additional Class Teacher/Form Tutor and Head of Department responsibilities
- Student information management with configurable student-number generation, contact and emergency-contact profiles, class-enrolment and status history, transfer/withdrawal records, and private student documents
- School health clinic for nurse/doctor student selection, timestamped visits, symptoms, observations, optional vitals, allergy information, prescriptions, doctor-only diagnosis, emergency contacts, visit history, and detailed student/current-visit PDFs with authenticated QR report links
- School reception visitor management with expected-visit registration, active check-in/out, duplicate active-phone protection, private visitor photos, audit-logged record corrections, print-ready QR badges, and authenticated badge verification
- Authorized past-paper ingestion to private Firebase Storage, with school metadata catalogued in Supabase

The academic modules whose backend schema exists but which do not yet have complete interaction screens are intentionally not presented as finished workflows. The authorized-paper ingestion pipeline stores files privately; a signed download/viewer endpoint is not included yet.

## Global command palette

After signing in, use the **Search** control in the workspace header or press **Ctrl+K** (Windows/Linux) / **Cmd+K** (macOS). Search accessible pages, role-authorized actions, settings, and school records. Use the arrow keys to navigate, Enter to open, and Escape to close. Favorites are saved to the signed-in user's school-scoped profile; recent destinations and recent search terms remain in browser memory/storage scoped by user and school.

Record search is performed by the `search_school_command_records` Supabase RPC and is limited to the active school, existing row-level security, enabled modules, and school permissions. Invoice search requires finance access. Search analytics store event metadata and HMAC digests of terms that return no results; raw query text is not stored. Metrics can be queried by authorized school administrators or users with audit-view permission using `get_command_search_metrics`.

Apply `app/supabase/migrations/202610310001_global_command_palette.sql` before deploying the frontend. Its student-name trigram index uses an immutable concatenation expression accepted by PostgreSQL. The migration creates the record-search indexes, user favorites, analytics tables, and access-checked RPCs. To extend the palette, add navigation results through the existing accessible sidebar routes, add role-gated actions in `actionsForRole`, and add settings destinations to `settingsItems`; ensure each action's destination handles its query parameters and keep any record search school-scoped and permission-checked in the database.

## Grouped workspace navigation

The workspace sidebar groups the existing routes into Academics, People, Finance, Learning & Library, Student Life, School Operations, Website & Communication, and Administration. The dashboard remains standalone; account security and authorized settings stay in the fixed footer area. Items are filtered by the current membership role, school module settings, and permission summary, while existing route guards remain responsible for direct URL access.

Groups expand independently and the group containing the current route opens automatically. The desktop sidebar can switch to a compact icon-only mode; its group icons expand their child links, with tooltips identifying the destinations. Both the expanded/collapsed mode and open groups are stored in browser local storage using a key scoped to the signed-in user and active school. The mobile drawer keeps labels visible and uses the same grouped navigation. No database migration or new role is required.

## Setup checklist and data health

School administrators and academic coordinators can open **Setup & Data Health** from Administration. Run a server-side health check to see weighted school readiness, category checks, and readiness for timetables, attendance registers, reports, fee invoicing, and daily operations. Results contain configuration statuses and aggregate affected counts, not student, staff, or financial record details. The server verifies the caller's school role and scopes every evaluation to the requested school.

Severity weights are critical 5, high 3, medium 2, low 1, informational 0. Passed checks earn their full weight; warnings and needs-review checks earn half; failed checks earn zero; checks that do not apply are excluded. The score is earned weight divided by applicable weight. A critical failed blocker prevents a Ready label; otherwise the overall labels are Not Configured (no applicable checks), Needs Attention (critical blocker or score below 50), Partially Ready (50–74.9), Nearly Ready (75–89.9), and Ready (90 or above). Workflow readiness also reports intentionally disabled modules as Module Disabled. Fee checks are excluded when finance is disabled. Fee categories and payment-method checks are not reported because the current schema has no separate fee-category or payment-method configuration tables.

The latest successful snapshot is persisted. Relevant school profile, academic, class, subject, staff, student, module, attendance, fee, and website changes mark it stale; a stale snapshot is refreshed when a user returns to the centre, and snapshots older than 24 hours are also considered stale. Failed evaluations are shown as errors and do not replace the last successful snapshot. Completed run records retain the requesting user and timestamps. The System Owner dashboard provides a separate read-only cross-school overview of readiness scores and stale or unchecked snapshots; detailed school checks remain available only to authorized school administrators and academic coordinators.

Apply both pending migrations from the `app/` directory before deploying the frontend:

```powershell
npx supabase db push --project-ref <your-project-ref>
```

This applies `202610310001_global_command_palette.sql` and `202610310002_school_setup_health.sql` in order. The setup-health migration adds the persisted run/results/state tables, row-level security, access-checked RPCs, and stale-result triggers. Then deploy the frontend. Do not mark the remote database as updated until the CLI confirms both migrations completed.

## Academic and finance PDFs

Academic reports are generated from published assessment results with the school's configured grading boundaries and report template. Finance invoices, payment receipts and statements use the existing school-scoped invoice, payment, allocation, adjustment and balance data; PDFs do not create or alter financial transactions. Their shared jsPDF generator handles A4 output, repeated page headers, multi-page tables/cards, and page numbering. Academic report pages now cap result rows to fit A4 and display per-report page counts; the template preview no longer presents invented student marks.

Individual academic reports, invoices, receipts and statements can be issued into the private `school-official-documents` bucket. The issuance migration adds school-scoped references where applicable, versions, opaque random QR tokens, event/audit records, public metadata-only verification and role-checked access to the stored PDF through a 120-second signed URL. Authorized users can preview the actual generated PDF and download/print it. Existing QR PDFs for visitor badges, library materials and medical visit reports continue to use their feature-specific routes.

Before deploying the frontend changes, apply [`202610310003_school_official_documents.sql`](./supabase/migrations/202610310003_school_official_documents.sql) to the same Supabase project. From `app/`, run `npx supabase db push --project-ref <your-project-ref>` and confirm the migration completes; the app does not apply or deploy migrations automatically.

The browser generates the PDF and supplies its SHA-256 digest; the database does not independently render or validate document contents. Public verification confirms a registered reference and its status, not that arbitrary PDF bytes match the source records. Invoice and receipt references come from the existing finance records; report and statement references use the new database counter. Bulk exports, other document types, document-management/history UI, rate limiting, retention/legal holds, digital signatures and accessible-PDF validation remain incomplete. Do not expose private PDFs through public storage URLs.

The Android project is maintained separately in `app/mobile/` and reuses this web app's Supabase project and database. Apply the pending Android access migration before inviting mobile users. School administrators enable Android access and configure role/module availability in **Settings → Modules & features**; the System Owner can disable it globally in **Platform settings → Global feature availability**. Each enabled school gets its own QR to a shared APK download page; after sign-in the app uses that school's configured logo. EAS Update delivers compatible JavaScript/UI updates on app launch, while native changes still need a new APK. ## Data and access model

`auth.users` is the identity source. `profiles` stores the corresponding application profile, while `school_memberships` maps a user to each school and role. School records carry `school_id`; composite foreign keys prevent cross-school relationships. RLS policies authorize access in PostgreSQL, independently of frontend route visibility. Parents' access is constrained by `parent_students`; student academic records are restricted to the student, linked parent, authorized teacher, and school administrator.

The first administrator can create student, teacher, class, and subject directory records. To give a teacher account access, open **Staff & teachers → Invite teacher**, enter their full name, work email, and employee number, and send the invitation. The `staff-invite` Edge Function creates the teacher membership and linked staff/teacher profiles; deploy it with `npx supabase functions deploy staff-invite`. After accepting the email invitation, the teacher signs in at `/login` and is routed to `/dashboard`, which displays the teaching dashboard for the teacher role. Use the teacher's staff profile to assign classes, subjects, and responsibilities. Role access is granted by the school membership, not editable profile fields.

Assignment and timetable prerequisite fields use contextual empty states and a reusable quick-create drawer for teachers, classes, and subjects. These writes use the same school-scoped tables and RLS policies as the directories; class/subject/teacher eligibility is rechecked when saving. Apply `202610310005_assignment_prerequisite_validation.sql` to validate assignment prerequisites in PostgreSQL. Existing audit triggers record the resulting school-record changes. Teacher creation does not create login credentials; use **Staff & teachers → Invite teacher** when account access is needed.

## Security notes

- `.env` is excluded from version control; only the Supabase public URL and anon key are used by this browser client.
- Do not add a Supabase service-role key to Vite environment variables.
- The SQL migration enables RLS for application tables and keeps files in private buckets.
- Configure Supabase Auth, email delivery, backups, deployment redirects, and production monitoring before deployment.
- Test policies with separate administrator, teacher, student, and parent accounts before storing real student data.
